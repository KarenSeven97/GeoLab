## 技术选型

| 方案 | 对本项目的适配 | 主要成本 |
| --- | --- | --- |
| MapLibre GL JS + Three.js | MapLibre 管理道路底图、地图相机和交互；Three.js 管理浅色建筑几何、光照及阴影。优先推荐用于本项目的 2.5D 城市场景。 | 自定义图层需处理共享 WebGL 状态、坐标变换、深度、地面接影及阴影范围。 |
| CesiumJS | 支持全球场景、地形、3D Tiles、太阳照明和阴影；若以后以全球地形与大型三维数据为重点则有优势。 | 为当前参考效果定制底图、材质和 UI 的范围较大；第一版不需要其主要地形能力。 |

以上是针对本项目范围的工程判断，不是性能基准。若后续发现既有代码，应重新评估并优先复用。

新项目建议采用 Vite + TypeScript 的前端构建；界面可先用普通 DOM/CSS，避免为小型控制面板引入额外框架。阶段 1 核心依赖为 maplibre-gl、three，按实际需要加入可靠的 OSM 转 GeoJSON 工具。阶段 2 再加入 SunCalc、经纬度到 IANA 时区的解析能力及支持时区规则的时间库。依赖版本在实施时核对兼容性并锁定。

职责划分：

- map：底图、相机、缩放/旋转/平移、地图生命周期。
- data：搜索、建筑查询、请求取消、限流、缓存和来源元数据。
- buildings：Polygon/MultiPolygon、孔洞、建筑分段、高度解析与几何资源释放。
- simulation：位置、IANA 时区、唯一模拟时刻以及当地日期/时刻的编辑规则。
- solar：太阳方位/高度、日出日落和光源方向。
- ui：悬浮面板、数据状态、时间轴和播放控制。

建筑从阶段 1 就使用 Three.js 几何，避免阶段 2 为太阳阴影重建一套建筑渲染。地图使用 Mercator；以选定区域为局部米制原点，统一东、北、上轴，再转换到地图坐标。阶段 2 使用方向光和真实阴影贴图，建筑同时投影、接影，透明地面接影材质保留道路可见性；不使用预设阴影动画。

## 数据来源与约束

### 底图和搜索

优先接入可配置的 MapTiler 底图与 Geocoding API；需要项目账户、可用配额及适当限制的浏览器访问 key，私密凭据不得提交 Git。也可接入用户已有的兼容服务。当前没有配置或验证任何项目 key、付费方案或覆盖范围。

经纬度输入在本地解析并检查范围，明确输入顺序。城市/地址搜索走服务接口，失败时保留上一个场景。

不把 OSM 公共瓦片服务器作为默认生产基础设施，其无 SLA 并禁止批量预取；如使用必须遵守署名、缓存和请求规范。也不默认接入公共 Nominatim：其全应用上限为每秒 1 请求，禁止自动补全，且对生成式建站平台及开发者主动选择有额外限制。若确需使用，须由开发者知情选择并遵守完整政策。

### 建筑

MVP 候选为 OpenStreetMap 建筑数据，通过 Overpass 小范围按需读取；请求 building 与 building:part，保留 OSM 类型/ID、原始属性、获取时间、来源和高度推断方法。公共实例存在限流和负载限制，不承诺持续可用；正式运行需选择适用的数据供应或自托管方案。

优先级：

1. 有效 height / min_height：标记“数据源标注高度”，不宣称一定实测。
2. building:levels 等层数：按明确的层高假设推算，标记“按层数估算”。
3. 两者均缺失：使用可配置默认高度（初始建议 9 米），标记“默认估算”。
4. 轮廓缺失：展示无数据状态，不能生成虚构建筑冒充真实数据。

统一处理高度单位、非法值、孔洞和多多边形；优先 building:part 形成分段体块，防止与完整建筑外壳重复叠加。保留 OSM 署名和 ODbL 链接；可再分发的数据快照需记录其来源和许可。

### 时间与太阳（阶段 2）

SunCalc 负责太阳位置和事件计算，不负责地理时区查询。使用所选位置的 IANA 时区；唯一模拟时刻以 UTC instant 存储，当地日期、时间由时区派生，编辑时采用明确的夏令时重复/缺失时刻规则。修改日期保留当地时刻，修改时刻保留当地日期。正常日期显示 00:00—次日 00:00；夏令时切换日实际可能是 23 或 25 小时，需显式处理。

全年播放与一天播放是两个独立入口，采用互斥活动模式以免同时修改状态。时间变化仅更新太阳和画面，不触发建筑请求或场景重建。处理极昼、极夜、跨日、闰年、夜间停用太阳阴影；节气日期按年份取得，不永久写死四个日期。

## 主要风险

- 数据完整性：不同城市的轮廓、分段和高度差异大，所有估算必须可见。
- 视觉准确性：均匀拉伸外轮廓不足以表现截图里的阶梯建筑；必须支持建筑分段。
- 服务可用性：key、配额、CORS、限流、目标网络和中文搜索覆盖需实际验证。
- 坐标/深度：南北符号、米制缩放、地图旋转与光源坐标必须一致；用已知方向和尺度验证。
- 阴影边界：视野外建筑也可能遮挡视野内地面，需要缓冲区；低太阳高度时阴影很长，必须显示模拟范围，不能声称全城精确。
- 性能：大范围查询、复杂多边形、阴影分辨率和高 DPI 会增加负载；先限定区域并合批，再根据测量优化。
- 第一版假设地面水平，采用简化几何；不模拟复杂地形、天气、玻璃反射或室内采光。

## 阶段 1 实施顺序

1. 建立最小 TypeScript 项目、锁定依赖、启动与构建说明；配置可替换数据服务及不含凭据的环境变量示例。
2. 打通一处真实地点的底图与建筑数据，优先以纽约 Bryant Park 周边作为参考对照点，覆盖情况需查询后确认。
3. 接入经纬度、地址、城市搜索；完成加载、空结果、请求失败和重试状态，切换地点取消过时请求。
4. 建立建筑标准化数据结构，处理多边形、孔洞、分段、单位与高度来源；生成浅色屋顶及侧面的三维几何。
5. 实现相机联动与旋转、缩放、平移、倾斜和全屏；完成左上紧凑信息面板。底部给阶段 2 预留空间，不呈现可点击的假时间轴。
6. 对移动结束后的区域变化做去抖、范围限制和缓存；离开区域释放几何、材质和事件监听。
7. 实际运行开发服务和生产构建，浏览器逐项验证后记录结果，失败则先修复，不进入阶段 2。

## 阶段 1 验收清单（全部待执行）

- [ ] 地址、城市名和经纬度都能定位真实地点。
- [ ] 道路、地名及真实建筑轮廓位置对齐，建筑具有顶部、侧面及可解释高度。
- [ ] 能查看高度来源，统计区分标注高度和估算高度。
- [ ] 旋转/缩放/平移/倾斜不会令建筑漂移，面板操作不触发地图手势。
- [ ] 加载、无建筑、搜索失败、建筑接口失败和 WebGL 不可用都有明确反馈。
- [ ] 连续切换地点至少 10 次，无旧请求覆盖新地点、重复场景或明显资源持续累积。
- [ ] 正常交互不重复请求相同区域；来源署名始终可见。
- [ ] 构建成功，真实浏览器测试有记录（浏览器、设备、范围、建筑数量、帧率或帧耗时）。
- [ ] 若缺少数据服务配置或网络不可达，明确记录阻塞，不用假数据充当验收通过。

## 后续阶段

- 阶段 2：统一时间状态、全年/一天双时间轴、独立播放控制、太阳计算和真实几何阴影。验证同一地点冬夏至的太阳高度差、上午/正午/下午方向与影长，以及夏令时和极昼极夜。太阳正午不等于当地 12:00；用独立天文参考交叉验证，并用影长 = 建筑高度 / tan(太阳高度角) 的平地算例检验几何。
- 阶段 3：按参考图打磨面板比例、体块层次和阴影可读性；进行性能、响应式、连续播放和重复切换地点测试。验收通过后才标记完成。
